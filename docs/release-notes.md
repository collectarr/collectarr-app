# Release notes

Every GitHub release uses this order: Collectarr banner; `Changes since last release:`; separator; `What's Changed`, contributor credits and comparison link.

Write the most important changes as a short English list in `docs/release-summaries.json`, keyed by release tag (for example `v1.2.0`): an object whose `summary` is a list of one-line entries, shown one under another. Explain user-visible outcomes, group related work, and do not claim tests or compatibility that were not checked. This summary is distinct from the complete change list. Keep `CHANGELOG.md` Unreleased entries grouped by Features, Fixes, Refactors, Docs and CI & Build for release preparation.

`tool/release_notes.py` builds `What's Changed` from the complete commit range of each release: every commit once, oldest first, with its author and commit link and the issues it or its pull request closes; merge commits and pull request titles are left out. GitHub's generated notes add New Contributors and the Full Changelog link. Lists that would exceed GitHub's description limit end with a link to the complete history. Without an editorial entry, the first changelog group of the release supplies up to ten rows.

Preview the newest release with `python tool/release_notes.py --repo collectarr/REPOSITORY`, or another one with `--tag vX.Y.Z`. Publish with the same command plus `--write`; `--all` backfills every published release. Drafts are excluded, and releases whose description is already current are not rewritten. Only release descriptions change: tags, versions, assets and databases are untouched.

The Release notes workflow runs after a successful Release workflow and formats the newest release; run it manually with a tag, or with Backfill, to apply an edited summary to existing releases. It checks out main with its tags and commits summaries imported for new tags to `docs/release-summaries.json`, so every published summary stays versioned. Pushing to protected main needs the `RELEASE_TOKEN` secret.

Each App release opens with its own banner, committed once as `vX.Y.Z.webp` to the orphan `release-banners` branch and linked at that commit, so it stays out of the release downloads and later artwork changes never alter past releases. Core and Sync releases have no banner. Do not delete the branch: past releases load their banners from it; a ruleset blocks deletion and force pushes. `tool/release_banner.py` fills the release dashboard artwork in `docs/assets/release-banner/` with the version, the publication date, six summary rows with an emoji each, the commits, merged pull requests and contributors since the previous tag, the first-time contributors, and the repository's open issues and stars at the moment the release was published (stars later withdrawn are not counted), so older releases can be rendered again with the same numbers. An entry in `docs/release-summaries.json` may be plain summary text or an object with `summary` and `items`: up to six `{"emoji", "text"}` rows of about 36 characters, with an emoji that matches each row. Without `items` the rows come from the first `feat` and `fix` commits, so write them for every release. Preview a banner with `python tool/release_banner.py --repo collectarr/REPOSITORY --tag vX.Y.Z --out banner.webp`, overriding any slot with `--set item_1=...` or `--set emoji_1=...`; it needs Pillow (`pip install pillow`). Replace a published banner with `tool/release_notes.py --tag vX.Y.Z --banner --write`.

The artwork is the release dashboard image with its placeholder text and row icons removed by inpainting; slot positions live in `SLOTS` in `tool/release_banner.py`. Text uses JetBrains Mono and Patrick Hand (SIL Open Font License, `OFL.txt` files alongside). Emoji are Noto Emoji images (Apache-2.0), downloaded while rendering from the pinned commit in `EMOJI_URL`.
